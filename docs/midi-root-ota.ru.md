# Яндекс Станция Миди: сохранение root ADB при переходе с factory-9 на .50

Практический отчёт от 27 октября 2026 года. Проверено на **одной Станции Миди, платформа `cucumber`**. Нужен уже полученный root на исходной прошивке. Это сохранение возможности доступа, а не получение root на произвольной закрытой прошивке.

## Что получилось

- До обновления: `0.9.1.14.2629069308.20241018.factory-9`.
- Подали штатному установщику оригинальный пакет `0.369.1.46.4778262955.20261013.160`.
- Затем штатный updater автоматически скачал и применил `.50` раньше, чем мы отключили обновления. Промежуточную загрузку `.46` по ADB непосредственно не зафиксировали.
- Итоговая версия: **`0.369.1.50.4794663100.20261021.160`**. Через сетевой ADB получили **`uid=0`**, оба подготовленных маркера сохранились. После этого восстановили SSH.

Это подтверждает результат на указанной `.50`. Прямой переход factory-9 → .50, другие модели, будущие OTA и повторная перезагрузка уже подготовленной .50 отдельно не проверялись.

## Почему это работает

В исследованных `.46` и `.50` штатный `onboot.sh` вызывает:

```sh
/system/vendor/quasar/activate_adb.sh check
```

Скрипт учитывает файлы в `/data/quasar/`. Маркер `activate_adb_glagol` разрешает активацию, а `activate_network_adb` выбирает сетевой ADB. При штатной деактивации скрипт пытается удалить маркеры. Если они защищены атрибутом **immutable**, удаление не проходит; оставшийся маркер активации также не даёт этому скрипту дойти до остановки ADB.

Старые factory-маркеры `/data/quasar_activate_*` не подходят: новая прошивка использует другой путь и удаляет старые файлы. Нужны именно указанные ниже имена.

Перед обновлением мы отдельно проверили эту логику на временных файлах в `/data` самой Миди: настоящий `chattr +i`, копии скриптов `.46`, заглушка вместо реального управления ADB. Boot check, деактивация `--quasmodrom` и `--all` оставили доступ включённым на уровне логики скрипта.

## Подготовка до OTA

Сначала сохранить резервную копию на ПК: файлы `/data`, конфигурацию и автозапуск, доступные разделы eMMC и boot-области. Дамп без рабочего способа восстановления не гарантирует спасение при повреждении загрузчика. В нашем случае кнопочный возврат с `.50` на factory-9 был проверен владельцем ранее; это не универсальная гарантия.

Следующие команды выполняются **в root-shell колонки до обновления**:

```sh
id -u
# Должно быть 0.

mkdir -p /data/quasar
test -e /data/quasar/activate_adb_glagol || touch /data/quasar/activate_adb_glagol
test -e /data/quasar/activate_network_adb || touch /data/quasar/activate_network_adb
chattr +i /data/quasar/activate_adb_glagol /data/quasar/activate_network_adb
lsattr /data/quasar/activate_adb_glagol /data/quasar/activate_network_adb
sync
```

У **обоих** файлов должен отображаться флаг `i`. При ошибке `chattr` не считать подготовку выполненной. Системный раздел для этих действий перемонтировать не нужно.

## Какой пакет использовали

Оригинальный [OTA для cucumber с сервера Яндекса](https://quasar.s3.yandex.net/cucumber/ota/user/8e1e25f9-1ff0-45cc-b30f-f920200539a5/0.369.1.46.4778262955.20261013.160.zip), также указанный в [каталоге quasar-unlock](https://github.com/otomir23/quasar-unlock/blob/main/src/manifests.json).

- Размер: `173266432` байта.
- SHA256: `5b7858a7e18130d5ab962566713cbe30ce63f3d09973983fee2752fd960f7dbb`.

Пакет не перепаковывали. Несмотря на расширение `.zip`, это пакет SWUpdate. Проверили хеш на ПК и после передачи на колонку. Не путать `cucumber` с отдельной платформой `yandexmidi`.

После остановки своих расширений запускали штатный механизм factory-9, передав ему путь к проверенному файлу:

```sh
# Это уже запускает прошивку и перезагрузку, не команду проверки!
nohup /system/vendor/quasar/device_ota_update.sh /data/ota-cucumber-46.swu \
  > /data/ota-cucumber-46.log 2>&1 < /dev/null &
```

Путь в примере условный: файл нужно заранее передать туда и проверить. Во время записи нельзя отключать питание. Для повторения, которому важно остаться строго на `.46`, этой последовательности недостаточно: окно автоматического перехода на следующую версию в нашем опыте НЕ было закрыто.

## Проверка после загрузки

На ПК, подставив фактический адрес своей колонки:

```sh
adb connect <IP-колонки>:5555
adb -s <IP-колонки>:5555 shell
```

В открывшейся оболочке:

```sh
id -u
cat /system/vendor/quasar/version_full
lsattr /data/quasar/activate_adb_glagol /data/quasar/activate_network_adb
```

В нашем случае получили `0`, точную `.50` выше и два флага `i`. Десятиминутное ожидание сначала закончилось без доступа; позже ADB появился. Поэтому таймаут сам по себе не доказывает потерю root. Но и бездумно повторять прошивку или сбрасывать питание нельзя.

## После получения доступа

Мы восстановили прежний статический SSH-сервер и его init-скрипт. Файлы в `/data` сохранились, а системный автозапуск пришлось вернуть. Не переносите чужие SSH-ключи.

Дальнейшие OTA заблокировали отдельно: сохранили новые штатные оригиналы, удалили задачу `updatesd` из **фактического launch.json новой версии** и заменили `device_ota_update.sh` блокирующей заглушкой. Уже запущенный updater пришлось приостановить: launcher ещё держал старую конфигурацию в памяти. Это не автоматическая часть трюка с маркерами и не готовый универсальный скрипт для всех прошивок.

На момент отчёта есть незакрытый вопрос: remount корня обратно в `ro` вернул `EBUSY`, раздел остался `rw`. Повторный reboot и совместимость всех расширений ещё не проверены. Сохранение root не означает, что сторонний звук, службы и их автозапуск автоматически пережили обновление.

## Границы метода

Метод зависит от сохранения `/data`, атрибутов файлов и текущей логики запуска ADB. Новая прошивка может изменить пути, снять immutable, изменить аутентификацию или запускать ADB без root. Закрытие способа активации через сертификаты и облако само по себе не доказывает закрытие этого локального пути — на нашей `.50` он сработал.

Для снятия защиты нужен root и `chattr -i` на этих двух файлах. Это убирает защиту, но само по себе не отключает уже работающий ADB. Не открывайте порт ADB в интернет: в проверенной конфигурации он даёт root-доступ.
